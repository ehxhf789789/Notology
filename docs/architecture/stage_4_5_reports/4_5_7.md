## Why this matters

Stage 4.5.4 covered text_merge primitives. Stage 4.5.6 covered drag-in async flow. Stage 4.5.6.x
covered DirtyQueue. None of those exercised the **full same-note multi-device user flow**:
- Two devices opening the same note
- One edits text → other pulls (fast-forward vs conflict)
- One adds attachment → other gets it (polling latency)
- Both add attachments to same note simultaneously
- All of the above on **slow / jittery / partial-failure networks**

This audit closes that gap end-to-end with 40 scenarios spanning 9 dimensions.

Inlined (production semantics reproduced exactly, dependencies too heavy to vendor):

- **`ref_sync::classify`** — LCA-based fast-fwd / divergence detection. The audit's
  `classify(local_head, remote_head, dag)` exhaustively enumerates `ancestors()` from both
  heads, returns `AlreadySynced` / `FastForwardPush` / `FastForwardPull` /
  `Diverged{ancestor}` matching the production decision tree.
- **`ConflictDetector::prepare`** — `branch_id = "{ts}_{sanitize(device)}_{head[..8]}"` (matches
  `conflict_detector.rs:48` byte-for-byte).
- **`BranchManager::save_conflict`** — `provider.put_branch(note, branch_id, payload)` ×2
  for both sides.
- **`adaptive_poller` tick** — `poll_tick(provider, last_known)` calls
  `provider.list_device_states()`, compares timestamps to `last_known` map, returns whether
  any change.

Slow-network jitter via LCG-driven `set_jittered_delay()` that mutates the provider's shared
delay between ops (deterministic seed for reproducibility).

## Findings (the production answers HanBin asked)

### Q1: A/B 동시 같은 노트 편집 + 첨부 시 동기화는 어떻게 되나?

**텍스트 편집**:
- A가 v1 push → B가 pull → **fast-forward** (A2) — B는 자동으로 A의 head로 이동
- A v1A push + B v1B push (둘 다 같은 v0에서 분기) → **conflict detected** (A3) — `Diverged { ancestor: v0 }` 반환, ConflictDetector가 branch_id 발급, BranchManager가 양쪽 branch를 provider에 저장 (A5), 사용자 resolve 후 한 쪽 삭제 (A6), 다른 device는 resolved branch만 봄 (A7)
- A와 B가 **같은 내용으로 동시 편집** → identical hash → conflict 없음 (A8, parallel-identical clean)

**첨부 등록**:
- A가 X 첨부 + B가 Y 첨부 같은 노트 → 두 ref 모두 보존, 다른 device 가 둘 다 pull (B1)
- A와 B가 **동일 파일 동일 이름** 같은 노트 → 두 device의 monotonic id 가 다르므로 2 distinct refs, provider blob은 dedup (B3)
- macOS NFD ingest + Windows NFC ingest 같은 노트 → Stage 4.5.5 NFC 정규화로 같은 sha + 같은 name → 1 blob 수렴 (B4)
- A 5개 + B 5개 동시 → 10 unique ids, C가 pull 시 모두 같은 노트에 link (B5)

**텍스트 + 첨부 동시**:
- A 텍스트 + 첨부, B 텍스트 (다름) → 텍스트는 conflict, 첨부는 정상 pull (D3) — **두 도메인이 독립적**

### Q2: A에서 첨부 등록 → B에 즉시 반영되나?

- **즉시 X — polling 모델** (4 tier: Realtime 1.5s / Active 5s / Idle 60s / Background 120s)
- Realtime tier polling 시 ~1.5s 안에 detect (C2: 215ms 측정, 100ms tick 사용)
- 정적 상태 (변화 없음) 에서는 false positive 0 (C3)
- 두 device 가 거의 동시에 push 한 변경은 한 번의 tick 에 모두 detect (C4)

**현실 latency**: A push → B 다음 polling tick 후 pull. 사용자 활성 (Realtime) ≤ 1.5s, idle (Background) 최대 120s.

### Q3: 약-신호 (느린 응답) 상황

| 상황 | 결과 |
|---|---|
| 1s / 3s / 5s / 10s latency | push 정상 완료 (E1-E4) — hard timeout 없음 |
| jitter 100-3000ms 변동, 5 ops | 모두 완료 (E5) |
| Slow A push + concurrent B push | 4.1초 (parallel ≪ serial 8초) — **lane independence** (F1) |
| Slow A + 동시 5개 drag from A | 5/5 succ (F2) — 큐 적체 정상 처리 |
| Fast B + Slow A | B 16ms, A 6초 — **device 간 완전 독립** (F3) |
| Slow pull | 정상 완료, 결과 정확 (F4) |
| put_object OK + put_md 실패 | 첫 시도 fail, retry 성공 (G1) |
| 10s slow op | false retry 안 일어남 — slow ≠ retry (G3, H1) |
| Mid-batch 1개 실패 | 9 succ + 1 fail, 다른 entry 영향 없음 (G4) |
| Offline 중 drag → 로컬 persist → online 후 push | 정상 flush (H3) |

**핵심 invariant**: slow 네트워크는 **timeout 으로 처리되지 않는다** (g3/h1). 약-신호 = 단순히 await 가 길어질 뿐. retry는 명시적 `Err` (NetworkError, NotFound 등) 받았을 때만 트리거. 사용자가 약-신호 환경에서 push 시 wait는 길지만 **데이터 손실/중복은 없음**.

## Findings (additional, informational)

### F-INFO-1 (slow-net cost is linear, not amplified)

E1 (1s × 2 ops) = 2.0s, E4 (10s × 2 ops) = 20.1s. 정확히 op 개수 × latency. 어떤 hidden retry / additional roundtrip도 없음.

### F-INFO-2 (parallel push가 serial보다 ~2배 빠름)

F1: A와 B가 동시 (4 ops × 2s 각각) — serial이면 8s, 실제 4.1s. **device 간 / lane 간 worker 가 진짜 병렬로 진행**.

### F-INFO-3 (text vs attachment domain 독립성)

D3: 텍스트 conflict 발생해도 attachment pull은 영향 0. 두 시스템이 분리된 path를 통해 진행되며, 한쪽의 conflict가 다른 쪽을 막지 않음.

### F-INFO-4 (production retry policy 검증)

H1: 단순한 slow op는 retry 트리거 X — production은 명시적 `Err` 만 5-strikes 카운트. 약-신호 사용자는 push wait는 길지만 retry-budget 소진으로 인한 drop을 겪지 않음.
