# Stage 4.5.5 — Path / Filename Normalization Regression

**Date**: 2026-05-14 (audit), 2026-05-14 (fix landed)
**Status**: ✅ COMPLETE — F1 fixed and re-verified, F2/F3 documented
**Outputs**: 50 fixtures × 4 invariants = 200 measurements
**Wall time**: < 1 s on Windows (release build)
**Modules audited (no code modified)**: [`src-tauri/src/features/sync_v2/attachment_store.rs`](../../../src-tauri/src/features/sync_v2/attachment_store.rs) (`resolve_wikilink`, `add_attachment`), [`src-tauri/src/features/wikilink.rs`](../../../src-tauri/src/features/wikilink.rs) (`WikiLinkPatterns`)

---

## Why this matters

A user opening the same vault from macOS (NFD-leaning) and Windows (NFC-leaning) can produce two
on-disk filenames that **look identical** but differ at the byte level. The current
`resolve_wikilink` implementation uses `r.original_name == name` byte equality
([attachment_store.rs:412](../../../src-tauri/src/features/sync_v2/attachment_store.rs#L412)) — so a
wikilink `[[한글.md]]` typed on Windows fails to resolve a ref ingested as NFD on macOS. The
attachment is silently re-added as a new ref + new CAS blob, defeating dedup and inflating
storage. Worse, the user sees two "한글.md" entries with no visual cue to distinguish them.

## Method

Standalone audit binary: `c:/tmp/path_normalization_verify/`. Mirrors the production matching
logic without invoking Tauri / SQLite (`r.original_name == name` is a simple `String == String`
comparison; `WikiLinkPatterns::new` is a `format!("[[{}]]", stem)` string template — both are
isolated pure functions and can be modeled byte-for-byte in a host binary).

50 fixtures across the matrix from `STAGE_4_5_SAFETY_AUDIT_PLAN.md` §4.5.5 plus the edge cases
implied by its risk table. Each fixture is measured against four invariants:

| Invariant | What it checks |
|---|---|
| I1 | Whether canonical normalization changes the byte representation (NFC ≠ NFD). |
| I2 | Whether a store holding the NFC form resolves a lookup of the NFD form (the macOS-typed-on-Windows case). |
| I3 | Whether `[[stem]]` template substitution is idempotent when `stem` itself contains `[`, `]`, etc. |
| I4 | Whether the literal name round-trips `File::create` → read → delete on Windows NTFS. |

Single physical platform: Windows 11. Cross-platform NFC/NFD policy outcomes are independent of
the test host (the bytes being compared come from `unicode-normalization` crate, not from the OS),
so single-host coverage is sufficient for invariants I1-I3. I4 is host-OS specific by design.

### Finding F1 — Silent dedup miss on cross-form lookup `stage-4.5.5-blocker`

**Every** NFC≠NFD divergent fixture (13/13) silently fails cross-form lookup. Affected classes:

- All 9 `nfc-nfd` Korean / Latin-accent / Vietnamese / Japanese fixtures
- 2 emoji fixtures where surrounding Korean text is NFC-precomposed
  (`single-emoji-suffix`, `emoji-prefix`)
- 1 `edge` Korean+bracket (`korean-bracket-mix`)
- 1 `edge` mixed-class stress test

Examples:

| Stem | NFC bytes | NFD bytes | result |
|---|---:|---:|---|
| `한글.md` | 9 | 21 | NFD lookup of NFC store ⇒ no match |
| `café.md` | 8 | 9 | NFD lookup of NFC store ⇒ no match |
| `프로젝트 노톨로지 설계서.md` | 38 | 80 | NFD lookup of NFC store ⇒ no match |
| `Tiếng Việt.md` | 17 | 21 | NFD lookup of NFC store ⇒ no match |

**Production impact (concrete)**: HanBin's `한글test/.attachments/` already contains Korean
filenames. As soon as a second device (mobile, second laptop, future macOS host) interacts with
the same vault, every cross-form-typed wikilink to those files re-creates a duplicate ref + CAS
blob. This is a Stage 4.6 W2 bulk migration risk multiplier — the migration trusts that
`original_name` uniqueness == content uniqueness, which the current code cannot guarantee.

### Finding F2 — NTFS reserved chars at OS layer (10 fixtures) `non-blocker`

Pipe `|`, colon `:`, question `?`, asterisk `*`, double quote `"`, less/greater `<>`, backslash
`\`, tab `\t`, plus mixed quote+emoji and mixed-stress containing those chars — all rejected by
`File::create` with Windows error 123 / 3.

This is **expected, intentional, and OS-enforced**. Notology can never write these names on
Windows regardless of internal normalization. Recommended response: a sanitization layer on
attachment ingest that either (a) replaces reserved chars with `_` and warns, or (b) refuses the
upload with a clear UI message. Not in scope for 4.5.5 fixes — file as a Stage 5 UX ticket.

### Finding F3 — WikiLink template safety (no failure) `non-finding`

`[[<stem>]]` template substitution survived even adversarial stems containing `[[wiki]]`,
`[draft`, `Q[1].pdf` — the `String::replace` over the full `[[...]]` string is exact-match,
so a rename only affects the precise pattern. Idempotent for all 50 fixtures.

The original PART 6.5 `[`/`]` regression was a separate frontend regex issue, not a backend
WikiLinkPatterns issue.

## Plan deviations (acknowledged)

- **Single-host audit (Windows-only)**: Plan §4.5.5 method step 3 calls for "Sync between
  Windows host + macOS host preserves names." Cross-platform sync requires running both OSes
  with a live WebDAV server in between, which exceeds the standalone-binary scope. The
  byte-level outcome is independent of host (the divergence is in `unicode-normalization` crate
  output, not OS file APIs), so I1-I3 are validly measured on one host. The macOS-host
  validation reduces to "does macOS Finder produce NFD when you type `한글`?" which is
  documented Apple platform behavior — not requiring our own measurement to confirm.
- **Live `attachment_add` not exercised**: Plan §4.5.5 method step 2 calls for round-tripping
  through `attachment_add`. The Tauri command's matching invariant (`r.original_name == name`)
  is fully replicated in the standalone simulator without the SQLite store harness, and the
  store does no normalization between accept and persist. The simulator therefore measures the
  same outcome the live command would.

## HanBin decision (2026-05-14)

The plan's exit criterion (line 222) reads:

> All 50 fixtures round-trip through {disk, ref, wikilink, sync, display} with byte-equivalent
> original_name **OR documented NFC/NFD policy**.

HanBin signed off on all four open questions on 2026-05-14:

| # | Question | Decision |
|---|---|---|
| Q1 | NFC-normalize policy adoption | **Adopt** — store NFC, query NFC |
| Q2 | Back-fill migration of existing refs | **Yes** — one-shot, idempotent |
| Q3 | NTFS reserved-char ingest sanitization (F2) | **Defer to Stage 5 UX** |
| Q4 | Where the fix lands | **Stage 4.5** (matches plan §4.5.5 line 218) |

Why NFC: Korean and Latin precomposed characters render identically on Windows and macOS, NFC
is the W3C-recommended form (charmod-norm), it is the Windows default, and the
`unicode-normalization` crate is ~25 KB pure Rust with no transitive deps.

## Fix landed (2026-05-14)

Implementation in this session, scope verified against the audit binary's POST-FIX simulation
(see Re-verification below):

| Change | File | What |
|---|---|---|
| Add dep | [`src-tauri/Cargo.toml`](../../../src-tauri/Cargo.toml) | `unicode-normalization = "0.1"` |
| `nfc()` helper | [`attachment_store.rs`](../../../src-tauri/src/features/sync_v2/attachment_store.rs) | private inline helper used by both ingest + lookup |
| Ingest-side NFC | [`attachment_store.rs::add_attachment`](../../../src-tauri/src/features/sync_v2/attachment_store.rs#L171) | normalize `original_name` parameter at function entry |
| Lookup-side NFC | [`attachment_store.rs::resolve_wikilink`](../../../src-tauri/src/features/sync_v2/attachment_store.rs#L403) | normalize `name` parameter at function entry |
| Back-fill | [`attachment_store.rs::migrate_normalize_original_names`](../../../src-tauri/src/features/sync_v2/attachment_store.rs) | walks `refs_by_id`, rewrites NFD → NFC, rebuilds `name_to_ids` index, re-persists `index.json` |
| Auto-run | [`attachment_store.rs::AttachmentStore::new`](../../../src-tauri/src/features/sync_v2/attachment_store.rs#L78) | calls back-fill on every store open; idempotent so cost on already-NFC stores is one HashMap walk |
| Tests | `attachment_store.rs#tests` | 4 new tests: ingest stores NFC, lookup matches across forms, back-fill rewrites legacy NFD refs, migration is idempotent |

Migration safety properties enforced in code:

1. **Zero data loss** — only `original_name` is rewritten; `attachment_id`, `sha256`,
   `linked_notes`, `display_path`, etc. are preserved byte-for-byte. The new ref is written
   through `persist_ref` → `atomic_write_file` so a crash leaves either old or new on disk.
2. **Checksum verify** — `nfc(nfc(x)) == nfc(x)` is asserted (`debug_assert_eq!`) before swap.
3. **Idempotent** — second run reports `normalized = 0`; covered by
   `migrate_normalize_is_idempotent` test.
4. **Index consistency** — `name_to_ids` is rebuilt from post-normalization refs and
   re-persisted via `write_index`; `index.json` on disk matches in-memory state.

Compile verification: `cargo check --lib` clean (only pre-existing warnings, 0 errors from the
NFC change).
