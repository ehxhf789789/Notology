## Why this matters

Stage 4 E2E tests ran the conflict path on 2-device scenarios. Real users on phone + laptop +
desktop can produce 3-way (and beyond) branch trees concurrently. The audit's job is to
verify that when multiple devices simultaneously diverge:

1. The text-merge algorithm produces predictable results (clean / conflict-marked) regardless
   of branch count.
2. Attachment collision-suffix allocation never produces overlapping `display_path` values.
3. The Stage-4.5.5 NFC normalization holds across devices (NFC-on-A vs NFD-on-B converges).
4. ConflictDetector's `branch_id` formula is deterministic, sanitizes hostile device names,
   and discriminates on every input axis (timestamp, device, head_hash).
5. `resolve_wikilink` works after a "device B reload of vault A's writes" simulation — the
   on-disk persistence layer round-trips cleanly.

## Method

Standalone binary at `c:/tmp/multi_device_conflict_verify/`. Vendors three production modules
via `#[path]`:
- `attachment_store.rs` (+ `file_io.rs` + `attachment_types.rs`) — for collision allocation
  and cross-device store reload simulation.
- `text_merge.rs` — for 3-way merge correctness.

`ConflictDetector::prepare`'s `branch_id` formula is reproduced inline (same `format!`
template + `sanitize`/`short_hash` helpers byte-for-byte) because pulling
`ref_sync::RefConflict` would drag in async sync-engine deps that don't add to the audit
invariant being measured. The reproduction is verified to match the production formula by
Stage-1 unit tests; this audit measures behavioral properties (determinism, sanitization,
discrimination) which the inline copy preserves exactly.

## Findings

### F-1 (non-blocker, **document-only**) — text_merge O(N·M) DP table cap

The first run of E2 attempted a 200K-line `three_way_merge` (1 MB markdown). The LCS DP table
allocation `vec![vec![0usize; m+1]; n+1]` evaluated to `200 001 × 200 001 × 8 bytes ≈ 320 GB`
and the process aborted with `memory allocation of 1600008 bytes failed`. This is **not a bug
in production semantics** — `text_merge.rs`'s docstring already pins the algorithm at "note-
sized text (typically <1000 lines)". The audit re-ran with a 1000-line input and passed.

**Recommendation**: surface this bound as a defensive guard inside `three_way_merge` —
either a fast path that returns "input too large to merge, please resolve manually" when
either side exceeds (e.g.) 5000 lines, OR migrate to an O(N+M) algorithm (Myers diff /
patience diff) if user notes might legitimately exceed that bound in the future. **Not
in scope for 4.5 — file as Stage 5/6 ticket.**

### F-2 (non-blocker, simulator-only) — adjacent-line replacements bundle into one conflict region

Class A scenario 10 confirms the `text_merge` module's documented limitation that an edit on
line 2 + an edit on line 3 (with no shared anchor between them) bundles both into a single
`<<<<<<<`/`=======`/`>>>>>>>` region. The user resolves manually. This is intentional and pinned by
test `merge_adjacent_replacements_yield_one_combined_conflict_region` in the production suite.

### F-3 (informational) — ConflictDetector inline reproduction matches production formula

The inline `branch_id` reproduction in this audit matches the formula in
[`conflict_detector.rs:48`](../../../src-tauri/src/features/sync_v2/conflict_detector.rs#L48)
character-for-character. Class D's 5 scenarios (determinism, device/hash/timestamp axes,
hostile-char sanitize) all pass, providing independent verification that the formula has the
intended properties:
- pure-deterministic (same input → same id)
- discriminates on every input axis
- sanitizes `/`, `:`, `*`, `<`, `>`, `|`, `\`, `"`, etc. to `_`
- output is filename-safe and deterministically sortable
