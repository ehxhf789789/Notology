## Why this matters

The drag-in user flow chains: drop file → `add_attachment` → `DirtyQueue.enqueue(AttachmentUpsert)` → `PushWorker` → `attachment_sync::push_attachment` → `provider.put_object` + `provider.put_md(ref)` → other devices' polling tick → `provider.get_md(ref)` → `provider.get_object` → local persist + `load_from_disk`.

Stage 4.5.4 covered the synchronous primitives (text_merge, branch_id, allocate_display_name).
Stage 4.5.6 covers the **async push/pull layer** — concurrency, network failure, multi-device
race, conflict detection, edge cases — the things that only surface when an actual sync runs.

## Method

Standalone async simulator at `c:/tmp/drag_in_flow_verify/`. Tokio multi-threaded runtime
(4 worker threads) drives 33 scenarios that exercise concurrent `tokio::spawn` tasks against:

- **Real production AttachmentStore** (vendored via `#[path]`) — full add/delete/lookup logic
- **Real production InMemorySyncProvider** (vendored via `#[path]`) — full async trait impl,
  including `fail_next()`, `set_delay()`, `partition_network()` controls
- **Inline `drag_in_and_push` + `pull_attachment`** — minimal reproductions of
  `attachment_sync::push_attachment` semantics: drag-in → `add_attachment` →
  `provider.put_object(blob)` + `provider.put_md(ref_json)`. Pull: `provider.get_md(ref)` →
  conflict check (same id, different sha) → `provider.get_object(blob)` → local persist +
  `load_from_disk`. The full `PushWorker` + `BackgroundWorker` + `DirtyQueue` (SQLite)
  scheduling layer is OUT of scope so we measure the algorithm, not the worker scheduling.

## Findings

### F-1 (informational, **Stage 4.5.3 F-1 fix verified end-to-end**)

E3 confirms the 17-digit attachment_id ms-precision fix holds across **two devices doing
rapid concurrent drag-in**. 200 attachments / 200 unique ids. Pre-fix this scenario would
have produced a tight cluster of duplicate ids across devices that race to the same wall-clock
second.

### F-2 (informational, **Stage 4.5.5 F-1 fix verified end-to-end**)

E2 confirms the NFC normalization fix holds across **devices ingesting different unicode
forms**. macOS-style NFD ingest + Windows-style NFC pull → 1 sha → 1 blob at provider →
deduped. Pre-fix this would have produced 2 distinct refs at provider with no convergence path.

### F-3 (informational, **production behavior verified**) — local-persists-on-network-fail

D1 + D5 verify the production guarantee that drag-in is committed to the local AttachmentStore
**before** the push attempt. If the network is down, the user's attachment is safe locally and
the upload retries on next sync. There is no path where the user's drop "disappears" because
the push fails.

### F-4 (informational, **provider idempotency verified**) — half-push recovery

D3 confirms that interrupted pushes (object up, ref down — or vice versa) recover cleanly:
re-issuing both `put_object` + `put_md` is idempotent; the provider does not duplicate. This
matters because Stage 4.6 W2 bulk migration may abort partway and need to resume.

### F-5 (informational, **conflict detection works**) — explicit error surface

E1 + E4 verify that **a remote ref with the same attachment_id but a different sha is
detected and surfaced as an error** (`CONFLICT id=… local=… remote=…`). The pull path
does NOT silently overwrite the local ref. This means a user whose two devices independently
edit the "same" attachment (rare but possible) will get an explicit conflict the user can
resolve, instead of one device's edit silently losing.

The full UI-side resolution (3 options: UseLocal / UseRemote / KeepBoth from
[`AttachmentResolution`](../../../src-tauri/src/features/sync_v2/conflict_detector.rs#L111))
was already audited in Stage 4.5.4 — this audit confirms the **detection** that feeds it.

### Out of scope (acknowledged)

- **DirtyQueue (SQLite WAL) scheduling**: this audit calls push/pull directly. The
  production path enqueues `AttachmentUpsert` to a SQLite-backed queue and a `PushWorker`
  drains it on a 1.5 s debounce. Queue consistency under crashes is a separate audit
  (already covered by `tests/sync_v2_e2e.rs` S5/S6 in part). Track as
  `stage-4.5.6-followup-dirty-queue-soak`.
- **Real WebDAV provider** (Synology Drive): the `WebDavProvider` implements the same
  trait, but its quirks (If-Match rejection, ETag semantics — see `project_synology_issues`)
  are not exercised here. The InMemoryProvider gives semantic correctness; real-provider
  testing is the existing S1-S9 e2e suite.
- **Frontend drag-drop event handler** (React/TipTap): not audited. The Tauri command path
  is from the React side `invoke('attachment_add', ...)` — that command is the same
  `add_attachment` audited here, so the backend invariants hold regardless of which UI
  triggered it.
