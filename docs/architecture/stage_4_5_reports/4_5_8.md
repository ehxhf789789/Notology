## Why this matters

Stage 4.5.1–4.5.7 (8 sub-stages, ~239 scenarios) all used `InMemorySyncProvider` — semantically
correct but artificial. Real Synology NAS has known quirks documented in
[`memory/project_synology_issues.md`](../../../memory/project_synology_issues.md):
- If-Match rejection (412 on all formats)
- Weak ETag format (`W/"..."`)
- Concurrency limit (4 max safe)
- Recursive MKCOL needed (parent dirs auto-created)

The (A) attempt — `cargo test --test sync_v2_e2e --release` against the same NAS — **was blocked
by the same `STATUS_ENTRYPOINT_NOT_FOUND (0xc0000139)` Windows DLL loader bug** that prevented
`cargo test --lib` since Stage 4.5.1. Both pathways fail at the link stage. The standalone
binary pattern (vendor via `#[path]`) is the only working approach.

This audit covers what InMemoryProvider can't: real network latency, real Synology's
HTTP/WebDAV semantics, real ETag format, real MKCOL behavior, real connection pooling.

## Findings

### F-1 (intermittent, **non-blocker**) — MKCOL race on 4 concurrent put_md to NEW directory

**First run**: D3 (4 concurrent put_md to fresh `d3/` dir) → **1/4 succ**.
**Second run** (after fixing test scenario sha256 issues, re-running same test): **4/4 succ**.
**Control D3a** (4 concurrent put_md to **pre-existing** `d3a_existing/`): 4/4 succ both runs.

The contrast between D3 (race-prone, intermittent) and D3a (no race, deterministic 4/4)
isolates the cause: **`WebDavClient::ensure_parents()` is not race-safe**. When 4 tokio tasks
concurrently call `put_md("d3/conc_N.txt", ...)` and the parent `d3/` doesn't exist, all 4
race to MKCOL it. Synology returns success for one and 405/412 (or similar) for the others
that lose the race.

**Why this is non-blocker**: Production code path is `PushWorker::process_batch` which has a
`for entry in entries { mark_retry on Err }` for-loop pattern (verified in 4.5.6.x). A
transient MKCOL race fail → `mark_retry` → next worker tick succeeds (dir now exists from the
winning task). User-visible effect: a single retry-cycle delay (~1.5 s debounce) on the first
multi-attachment add to a never-before-used directory.

**Production impact (concrete)**: A user dropping 10 attachments simultaneously into a brand-new
note (which creates a never-before-used `.attachments/` dir) might see 1-3 of them stay in the
queue for one extra retry cycle. They eventually all upload. **No data loss.** No silent miss.

**Recommended fix** (Stage 5/6 ticket): pre-emptive `MKCOL` of common parents as a single call
before queue drain begins, OR a per-path mutex inside `WebDavClient::ensure_parents()` so only
one task per path issues the MKCOL.

**Ticket**: `stage-4.5.8-followup-mkcol-race`

### F-2 (informational, **production behavior verified**) — content-hash validation on get_object

**Discovered during initial scenario authoring**. WebDavProvider's `get_object(sha)` validates
that the SHA256 of the retrieved content matches the path-derived hash. Our first iteration
used fake hashes (`"abc1234..."`) and got `Other("Hash mismatch for ...: expected
abc1234..., got <real-sha256>")`. Test scenarios were rewritten to use real SHA256.

**Why this is good**: Production code self-validates that the blob the NAS hands back is the
blob requested. **Tampered or corrupted NAS storage cannot silently substitute different
content** — it is detected immediately on read. This is a strong integrity property that the
4.5.7 InMemoryProvider audit could not verify.

### F-3 (informational, **Synology quirks confirmed**) — three production adaptations all work

D1 confirms `normalize_etag()` strips `W/` prefix (Synology returns `W/"..."` format).
D2 confirms no-If-Match policy (PUT without precondition succeeds, version changes deterministically).
D3a confirms 4-concurrency works fine on existing dirs. D5 confirms per-device state file
pattern (D8 design — replaces If-Match) works with PUT/list semantics.

### F-4 (informational, **performance baseline**) — NAS round-trip ~150 ms avg

26 ops in 4.5 s wall time, ~150 ms per op average over public Internet WebDAV/HTTPS. Useful
baseline for Stage 4.6 W2 bulk migration cost estimation: 17 attachments × 2 ops (put_object +
put_md) × 150 ms ≈ 5.1 s for the W2 migration's NAS-bound work. Within Plan §4.5.3 target
(< 60 s CPU initial sync).

### F-5 (informational, **Korean path support confirmed**) — D4

`d4_한글/회의록.txt` (UTF-8 encoded Korean) round-trips PUT + GET successfully on Synology
WebDAV. No URL-encoding issues. Combined with Stage 4.5.5 NFC normalization, Korean
filenames are end-to-end safe.

## Out of scope (acknowledged)

- **Real concurrent multi-device** (two physical devices simultaneously editing): standalone
  binary simulates two devices via separate WebDavProvider instances against same NAS prefix,
  but cannot exercise OS-level network stack contention from two physical machines.
- **Synology Drive client conflict**: this audit hits the WebDAV endpoint directly. Synology
  Drive's own client is a separate sync layer that may produce its own `(SynologyDrive
  Conflict ...)` filenames — covered by `conflict_detector::detect_synology_conflict` (regex)
  but not exercised here.
- **Long-duration NAS soak** (24h continuous): out of audit scope, would need CI runner.
