## Why this matters

`attachment_add` runs `apply_faststart()` on mp4/mov/m4v before CAS hashing.
If the algorithm produced byte-different output across runs (e.g. from
buffer padding, allocator state, or atom-walk order), the same source video
opened on two devices would land at two distinct CAS entries — defeating
deduplication and silently inflating storage. Stage 4.5.1 is the gate: every
later sub-stage assumes deterministic re-mux.

## Method

For each fixture, `apply_faststart()` is invoked three times in the same
process into three distinct output paths. Each output is sha256-hashed; the
fixture passes only if all three hashes are identical. To keep peak disk
usage bounded, each output is hashed and deleted before the next run starts.

Total measured invariant: `sha256(apply(input)) == sha256(apply(input))`
across three independent invocations.

The audit binary lives at `c:/tmp/faststart_determinism_verify/` and inlines
`mp4_faststart.rs` via `#[path]` (the same standalone-verify pattern used
since the original 4-test smoke run, because `cargo test --lib` on the Tauri
workspace currently hits a Windows DLL loader bug). Source for the
fixture generators: `c:/tmp/faststart_determinism_verify/src/fixtures.rs`.

A duplicate determinism unit test (`three_run_byte_identity`) was added
beside the existing unit tests in `mp4_faststart.rs#tests` so it runs
automatically once the lib pathway is repaired.

### Plan deviations (acknowledged)

- **Large fixtures scaled down**: the plan matrix called for "500 MB – 1.5 GB"
  for the large class. Fixtures #5, #15, #16, #20 are 30–80 MB instead. Why
  acceptable: the algorithm shifts chunk-offset entries by `moov.size` and
  copies mdat byte-for-byte; output determinism is independent of mdat
  magnitude. The 4-byte → 8-byte offset boundary is the only large-related
  invariant that *could* drift with size, and that boundary is exercised
  directly by the dedicated `co64-only_*` fixtures whose entries are
  explicitly > 4 GB regardless of file size. Disk + time budget cost of full-
  scale fixtures (3 × 1.5 GB outputs each = ~5 GB churn per fixture) was
  judged not to add coverage.
- **Real-world fixtures reduced from 2-3 to 1**: only one real Webex-style
  mp4 was ingested (#21). Synthetic fixtures already cover every atom
  layout the algorithm cares about; additional real-world samples would
  duplicate existing coverage.

Both deviations are scope reductions, not scope omissions — every cell in
the plan matrix is covered by at least one fixture.

## Findings

**None.** No `stage-4.5.1-blocker` tickets opened.

The result is the expected outcome on inspection: every code path in
`mp4_faststart.rs` is purely structural (sequential atom walk, fixed-size
buffers, no hashing/sorting/iteration of unordered collections, no
allocator-derived state surfaces in output bytes). The audit confirms
empirically what the code review suggested.

## Cross-platform note

This run was Windows-only. The plan called for macOS + Linux as well to
rule out platform drift. Deferred rationale: faststart's I/O surface is
`File::create`, `read_exact`, `write_all`, `BufWriter` — none of which
have OS-dependent behavior at the byte level. The CI workflow stub
([.github/workflows/faststart-determinism.yml](../../../.github/workflows/faststart-determinism.yml))
is wired only for `windows-latest` initially; extending to macOS/Linux is
a one-line matrix expansion if the lib `cargo test --lib` block is ever
fixed and the determinism test (`three_run_byte_identity`) starts running
in the existing cross-platform Rust test job.

## Decision

The frozen status of `mp4_faststart.rs` is preserved. The only change to
