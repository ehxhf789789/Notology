## 2. Discovery during implementation

Plan §4.1 wrote: *"RightPanel: tab-row at top selecting Calendar / Tags /
Comments / Outline / Metadata. Replaces today's 'calendar visible by default,
others slot-mounted invisibly' pattern."*

Code audit revealed a different reality:

| Component | Location | Owner |
|---|---|---|
| `RightPanel.tsx` (calendar) | `src/core/layout/` | Vault-wide aggregate memos |
| `TagPanel.tsx` | `src/features/tags/` | **Mounted in `HoverEditor.tsx`** — per-note |
| `CommentPanel.tsx` | `src/features/comments/` | **Mounted in `HoverEditor.tsx`** — per-note |
| `YamlEditor.tsx` (Metadata) | `src/features/metadata/` | **Mounted in `HoverEditor.tsx`** — per-note |
| (Outline) | — | Does not exist yet |

Slot registry (`SlotRegistry` in [`slotRegistry.ts`](../../../src/core/infrastructure/slotRegistry.ts)) has only 2 active registrations: `editor-banner` + `sidebar-footer-status`. No right-panel slots. Plan §4.1 was aspirational, not descriptive.

**Decision**: land the tab-row layout now (immediate value), plumb the 4 per-note tabs as `<Slot name="right-panel-{tags|comments|outline|metadata}" />`. When no slot is registered (current state), the tab shows `<EmptyState>` explaining the panel is per-note and the user should open a note to populate it. Future sub-stages (5.0.4 editor work or beyond) can register slots that subscribe to a focused hover-window's filePath.

This:
1. Lands the visual layout matching plan intent
2. Solves calendar discoverability immediately
3. Adds plumbing for per-note content without coupling to hover-window state
4. Maintains "Core ↔ Feature via Slot" architectural rule (CLAUDE.md §아키텍처 원칙)

## 3. Changes landed

### 3.1 `uiStore.ts` — new `rightPanelTab` state

- `RIGHT_PANEL_TABS = ['calendar', 'tags', 'comments', 'outline', 'metadata']` exported as const
- `type RightPanelTab` derived from that
- `rightPanelTab: RightPanelTab` state, default `'calendar'`
- `setRightPanelTab(tab)` action persists to `localStorage` (`notology-right-panel-tab` key) following the existing pattern used by `sidebarWidth`
- `useRightPanelTab()` selector hook + barrel re-export in `zustand/index.ts`

### 3.2 `RightPanel.tsx` — rewritten as `<Tabs>` container

- Header preserved (today's date indicator + close `<IconButton>`)
- `<Tabs value={activeTab} onChange={setRightPanelTab}>` consumes the new state
- `<TabList>` has 5 tabs, each with a Lucide icon and Korean/English label
- Tab content lifted into local components:
  - `<CalendarTabContent>` = full pre-5.0.3a calendar implementation (memos, month grid, view-mode toggle, resolve-toggle, hover-window-open on click) — zero behavior change
  - `<SlotOrEmpty name="right-panel-tags|comments|outline|metadata" perNote />` for the four per-note tabs — renders `<Slot>` if registered, else `<EmptyState>` from 5.0.2a primitives
- `useTodayMemoCount()` hook preserved (exported API for collapsed-bar consumers)
- Old hardcoded calendar layout (header + calendar + divider + memo list) re-used as-is inside `<CalendarTabContent>` — preserves all keyboard / interaction / refresh behavior

### 3.3 `Sidebar.tsx` — right-panel toggle button (calendar discoverability fix)

The `.sidebar-actions` row in the header now has a third button:

```tsx
<Tooltip content={t('rightPanelToggle', language)} placement="bottom">
  <IconButton
    icon={<PanelRightOpen size={16} />}
    aria-label={t('rightPanelToggle', language)}
    variant="ghost"
    size="md"
    pressed={showHoverPanel}
    onClick={() => uiActions.setShowHoverPanel(!showHoverPanel)}
  />
</Tooltip>
```

This is the **first time** design-system primitives (`<IconButton>` + `<Tooltip>`) are consumed by production code. Validates the 5.0.2a/b API surface against a real use-case. `aria-pressed` reflects open-state on toggle.

### 3.4 i18n (Korean + English)

13 new keys added to both `ko` and `en` blocks:

`rightPanelTabsLabel`, `rightPanelCalendar`, `rightPanelTags`, `rightPanelComments`, `rightPanelOutline`, `rightPanelMetadata`, `rightPanelToggle`, `rightPanelEmptyTitle`, `rightPanelEmptyDesc`, `rightPanelEmptyPerNoteTitle`, `rightPanelEmptyPerNoteDesc`, `prevMonth`, `nextMonth`.

### 3.5 CSS (`hover-editor.css`)

- `.right-panel` gets `overflow: hidden` so the tab strip + content don't overflow the 280px panel
- New `.right-panel-tabs` / `.right-panel-tablist` styles — tab strip sits at top, content fills remaining space
- Korean labels (캘린더 / 태그 / 코멘트 / 아웃라인 / 메타데이터) don't fit horizontally in 280px ÷ 5; CSS hides the label `<span>` with modern sr-only (`clip-path: inset(50%)`) while preserving accessible name. Each `<Tab>` also gets `title` attribute → native browser tooltip on hover
- `.right-panel-tab-content` / `.right-panel-calendar-tab` — content area wrappers

All new rules use Tier 2 tokens only. Audit baseline (815 hex / 901 margin/padding px) **unchanged** — confirmed by `npm run audit:tokens`.

## 5. Calendar discoverability — RESOLVED

Before 5.0.3a:
- `showHoverPanel: false` default; cold-start always closed
- Zero visible UI to open right panel
- Only `Ctrl+→` or `Ctrl+Shift+C` keyboard shortcuts could reach calendar
- Plan §1.2 documented this as known gap

After 5.0.3a:
- Sidebar header has a clearly-visible `<PanelRightOpen>` icon button with tooltip
- Tooltip discovery via hover; click toggles
- `pressed` state communicates current open/closed
- Keyboard shortcuts still work in parallel
- Calendar is the default active tab → first visible content when user opens the panel

Confirms HanBin's 2026-05-15 plan choice (Option 1 — no separate hotfix, address in 5.0.3) was correct.
